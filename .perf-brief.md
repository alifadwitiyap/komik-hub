## Jawaban

**R1 — Hasil yang diinginkan:** semua aspek, prioritas utama: **membuka
series pertama kali terasa sangat lambat.**

Terukur, dan ini mengonfirmasi keluhan itu dengan angka:

| Skenario | Waktu |
|---|---|
| Series dingin (belum pernah dibuka) | **5.9 s** |
| Series dingin lain | **6.9 s** |
| Series sama, hit kedua (cache) | 0.004 s |

Jadi masalahnya bukan render atau jaringan user — hampir seluruh 6 detik itu
server menunggu sumber upstream. Cache series hanya **in-memory, TTL 300 detik,
maks 256 entri**, dan hilang setiap container restart. Tidak ada persistensi ke
disk, padahal `DiskCache` sudah ada di `komik/core/src/cache.rs` dan tidak
dipakai untuk series.

Konsekuensi: setiap series yang belum pernah dibuka dalam 5 menit terakhir
selalu bayar ~6 detik penuh.

Tambahan temuan: cache itu **bukan** stale-while-revalidate. Setelah TTL habis,
request berikutnya menunggu hitung ulang penuh (union 4 sumber) secara blocking
— tidak ada penyajian data lama sambil refresh di latar. Jadi pola "6 detik tiap
5 menit" berulang terus, bukan sekali per series.

**R2 — Batasan yang diterima:** daftar chapter boleh telat **~10 menit**. Ini
membuka dua hal yang sebelumnya tertutup:

- TTL cache series 300 s memang sudah di dalam anggaran (aman), tapi angka itu
  belum cukup untuk menghapus rasa "6 detik" karena entri hilang saat restart.
- Persistensi ke disk jadi sah: `/data` sudah di-mount sebagai volume di
  `docker-compose.prod.yml:34`, jadi cache yang ditulis ke `/data` selamat dari
  redeploy. `DiskCache` di `komik/core/src/cache.rs` sudah ada dan tinggal
  dipakai untuk series.

Yang tetap tidak boleh: menyajikan data lebih tua dari ~10 menit tanpa
memberitahu user.

**R3 — Kriteria keberhasilan:** series yang dibuka harus terasa **1–2 detik**.

## Temuan yang mengubah arah (bukan asumsi)

**1. RAM bukan bottleneck.** Container prod dibatasi `mem_limit: 512m`
(`docker-compose.prod.yml:42`), dan pemakaian nyata hanya **14 MB**. Menambah
RAM 16 GB tidak menyentuh aplikasi sama sekali selama batas 512 MB belum
dinaikkan — dan menaikkannya pun tidak akan mempercepat apa pun, karena
bottleneck-nya I/O jaringan ke sumber, bukan memori. Rencana "cache lebih besar
di RAM" tidak akan menghasilkan apa-apa.

**2. ~~Kompresi HTTP tidak ada.~~ SALAH — sudah dikoreksi.** `deploy/Caddyfile`
memang tidak punya `encode`, tapi `komiku-server/src/main.rs:85` memasang
`CompressionLayer` (tower-http gzip) untuk semua respons, termasuk aset SPA.
Diukur pada payload nyata: `/api/unified/series` 18.684 → 2.352 byte (87%),
`react-vendor.js` 257.124 → 80.714 byte (69%). Pengukuran pertama saya memakai
`curl -I` (HEAD) yang tidak memicu kompresi — itu sumber kesalahannya.
**Tidak ada pekerjaan yang dibutuhkan di sini.**

**3. Cache series hilang saat restart, dan tidak pernah menyajikan data lama.**
`series_cache` = in-memory, TTL 300 s, maks 256 entri, tanpa persistensi. Tiga
sumber lain sudah punya `DiskCache` (`komik/core/src/cache.rs`) tapi server
memakai `Cache::memory` (`aggregator.rs:320`). `/data` sudah jadi volume, jadi
disk cache akan selamat dari redeploy.

**4. Service worker sudah stale-while-revalidate untuk `/api`.** Artinya
kunjungan ulang dari browser yang sama sudah instan hari ini. Yang lambat adalah
**kunjungan pertama** — tidak ada SW cache, dan server belum punya entri.

**5. Biaya 6 detik itu dari upstream, bukan CPU.** Health check: komiku 443 ms,
mangaku 947 ms, shinigami 64 ms, kiryuu 613 ms. Tapi series dingin dari
shinigami (primary cepat) tetap **3.98 s** — karena fase B harus resolve judul
ke 3 sumber lain, dan komiku lambat (TTFB 5–9 s). Desain dua tahap
(resolve paralel → series paralel) sudah ada di
`collect_series_across_sources`.

## Konflik yang harus diputuskan

Target 1–2 detik **tidak mungkin** untuk series yang benar-benar belum pernah
dibuka: upstream sendiri butuh 4–6 detik, dan itu di luar kendali kita. Target
1–2 detik hanya realistis bila cache sudah terisi (disk + SWR → ~10 ms).

**Koreksi**: klaim "tidak ada kompresi" di atas SALAH. `komiku-server/src/main.rs:85`

API series 18.684 → 2.352 byte (87%), `react-vendor` 257.124 → 80.714 byte (69%).
HEAD request tidak memicu kompresi, itu sebabnya pengukuran pertama keliru.

### ⚠️ Koreksi klaim latency

Angka "−25% cold series" yang sempat ditulis di sini **tidak sah**. Dua kesalahan
pengukuran ditemukan saat verifikasi ulang:

1. **Harness lama tidak memvalidasi respons.** Skrip melaporkan
   `median=0ms ... LULUS` padahal 6/6 request balas `000` (koneksi ditolak).
   Median 0 ms dari koneksi gagal bukan "cepat" — skrip hanya membandingkan
   median ke budget tanpa memeriksa status HTTP. Harness sekarang gagal keras
   bila ada non-200 atau payload tanpa chapter.
2. **Backup `cp` menimpa source dengan versi optimized.** Saat menyiapkan
   baseline, `cp` menyalin file yang sudah berisi kode optimized ke `bk_*.rs`.
   Build "baseline" karena itu identik dengan optimized — dibuktikan dengan
   `cmp` pada kedua binary (ukuran sama persis). Perbandingan itu tidak mengukur
   apa pun.

Pengukuran yang sah harus memakai dua binary berbeda (diverifikasi `cmp`) dan
dijalankan bergantian (ABAB) agar drift jaringan tidak bias ke satu sisi.
Hasilnya ada di bagian "Uji A/B" di bawah.

### Uji A/B (dua binary berbeda, bergantian, cache kosong tiap run)

Metode: dua binary terpisah (`/tmp/srv_base` 283,9 MB vs `/tmp/srv_opt` 291,4 MB,
dipastikan **berbeda** via `cmp`), tiap run server di-restart sehingga cache
in-memory kosong, 8 id sama (4301–4308), 2 ronde bergantian baseline→optimized.

| | n | median | mean | min | max |
|---|---|---|---|---|---|
| baseline | 16 | **3396 ms** | 3325 ms | 2481 | 4333 |
| optimized | 16 | **2512 ms** | 2436 ms | 1783 | 3255 |

**Delta median = −26,0%** — konsisten di kedua ronde (−22,4% dan −26,5%),
jadi bukan artefak satu sampel.

Kontribusi per lane (diukur terisolasi, bukan end-to-end):

| Lane | Efek | Catatan |
|---|---|---|
| A (paralel) | kiryuu −0,23 s; shinigami 2-call 0,200→0,100 s | sumber non-primary, jarang jadi penentu |
| B (kanonik) | −0,358 s per series komiku | sumber primary, selalu kena |
| C (gzip) | byte −40% | menolong TTFB di link lambat, kecil di link cepat |

Catatan penting: endpoint `/api/unified/series` membayar **dua hop** (resolve
semua sumber paralel, lalu series semua sumber paralel). Karena komiku adalah
primary dan lane B memotong 0,358 s di hop-1, sebagian besar delta −26% datang
dari lane B, bukan dari paralelisasi lane A. Klaim "paralelisasi menghemat 25%"
karena itu **salah** — paralelisasi hanya menyumbang sebagian kecil.

### Verifikasi dependency/build (gate OMH served-surface)

Perubahan menyentuh metadata build (`Cargo.toml` + `Cargo.lock`), jadi
diverifikasi di tiga level: lockfile, feature graph, dan runtime.

**1. Lockfile — dependency benar-benar ter-resolve**

```
$ grep -A1 '^name = "flate2"' komik/Cargo.lock   → flate2 1.1.10
$ grep -A1 '^name = "brotli"' komik/Cargo.lock   → brotli 9.1.1
```

**2. Feature graph — fitur aktif, bukan sekadar ada di lock**

```
$ cargo tree -p komik-core -e features | grep reqwest
├── reqwest feature "brotli"
├── reqwest feature "gzip"
```

**3. Smoke runtime — dekompresi transparan terbukti**

`komik/core/examples/smoke_gzip.rs` memanggil `https://httpbin.org/gzip` dan
memeriksa tiga kontrak: status 200, `content-encoding` **dibuang** reqwest,
body ter-parse sebagai JSON, dan server mengaku `gzipped: true`.

```
$ cargo run -q -p komik-core --example smoke_gzip
status          = 200 OK
content-encoding= None
body len        = 199 byte
json valid      = ya
server gzipped  = true
LULUS: reqwest mendekompak gzip secara transparan (fitur aktif)
EXIT=0
```

**4. Kontrol negatif — membuktikan test tidak vakum**

Fitur `gzip`+`brotli` dicabut sementara, smoke dijalankan ulang:

```
$ cargo run -q -p komik-core --example smoke_gzip
Error: Error("expected value", line: 1, column: 1)
EXIT SEBENARNYA = 1
```

Body mentah masih terkompresi sehingga JSON gagal di-parse → exit 1. Fitur
dipulihkan, smoke kembali exit 0. Tanpa langkah ini, "LULUS" bisa berarti
test-nya tidak menguji apa pun.

**5. Project check**

```
$ cargo check --workspace --all-targets     → Finished, EXIT=0
$ cargo test -p komik-core                  → 165 passed, 0 failed
$ cargo clippy -p komik-core --all-targets -- -D warnings → EXIT=0
```

Catatan: `cargo run --example smoke_gzip` butuh jaringan ke httpbin.org, jadi
tidak dijadikan unit test di CI — ia smoke manual untuk memvalidasi fitur
dependency, bukan regression test.
